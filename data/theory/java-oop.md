## Главное в шести правилах
- **Виртуальны только методы экземпляра.** Поля, `static`- и `private`-методы выбираются по статическому типу выражения ещё при компиляции: их можно скрыть, но не переопределить.
- **Объект собирается сверху вниз**: сначала конструктор предка целиком, потом инициализаторы полей наследника, потом тело его конструктора. Переопределённый метод, вызванный из конструктора предка, видит поля наследника пустыми.
- **Перегрузку выбирает компилятор по статическим типам аргументов**, в три фазы: без упаковки и varargs → с упаковкой → с varargs. Внутри фазы побеждает самый специфичный метод, иначе — ошибка неоднозначности.
- **Константная переменная подставляется в место использования.** `static final` примитив или `String` с константным выражением класс не инициализирует, а её новое значение не видно без перекомпиляции потребителей.
- **Нестатический вложенный класс держит внешний объект.** Внутренний и анонимный класс могут хранить сильную ссылку `this$0`; `static`-вложенный класс и лямбда без обращения к `this` — нет.
- **`final` защищает ссылку, а не объект.** Неизменяемость — это защитные копии на входе и выходе, а не модификатор.

## Наследование и интерфейсы
- Переопределение может: расширить доступ (`protected` → `public`), сузить тип возврата до подтипа (ковариантный возврат), объявить меньше checked-исключений или ни одного. Unchecked можно добавлять свободно.
- Нельзя: сузить доступ, объявить более широкое checked-исключение, вернуть супертип.
- `static`-метод в наследнике **скрывает** родительский. Статический метод не может скрыть метод экземпляра, а метод экземпляра — переопределить статический: оба варианта не компилируются.
- Поля не полиморфны: поле с тем же именем в наследнике — второе поле, `p.name` берётся по типу `p`.
- `private`-метод не наследуется: одноимённый метод наследника — отдельный метод, а вызов внутри предка всегда идёт в свой `private`.
- `@Override` ставить всегда: он ловит и скрытие, и «переопределение» `private`, и опечатку в сигнатуре.
- Default-методы: метод класса или суперкласса побеждает default интерфейса; более специфичный интерфейс (наследник) побеждает родительский.
- Два несвязанных default с одной сигнатурой — ошибка компиляции; переопределить и выбрать явно: `A.super.hi()`.

## Конструктор и переопределяемые методы
```java
class Base { Base() { init(); } void init() {} }
class Child extends Base {
    private final List<String> items = new ArrayList<>();
    @Override void init() { items.add("x"); } // items == null → NPE
}
```
- Правило: из конструктора вызывать только `private`, `final` или `static` методы; сложную инициализацию — в фабрику.
- Ловушка-исключение: `final`-поле с константным инициализатором (`final String s = "x"`) метод увидит уже со значением — компилятор подставил литерал.
- **Java 25** (JEP 513, гибкие тела конструкторов): до `super()` можно присвоить поля своего класса без инициализатора в объявлении — `Child() { items = new ArrayList<>(); super(); }`, и `init()` их увидит. Читать поля и вызывать методы экземпляра до `super()` по-прежнему нельзя. В Java 21 операторы до `super()` запрещены.

## Перегрузка
- Фаза 1 находит `m(long)` для `m(5)` раньше, чем `m(Integer)` и `m(int...)`. Упаковка побеждает varargs: из `m(Object)` и `m(long...)` для `m(1)` выбирается `m(Object)`.
- `null` подходит любому ссылочному параметру: `log(String)` и `log(Integer)` несравнимы — «reference is ambiguous». Лечится приведением `log((String) null)`.
- **`List<Integer>.remove(1)`** — удаление по индексу (`remove(int)` в фазе 1), значение удаляют `remove(Integer.valueOf(1))`.

## Инициализация и константы
- Порядок при первом `new Child()`: статика `Parent` → статика `Child` → поля и блоки `Parent` → конструктор `Parent` → поля и блоки `Child` → конструктор `Child`. Статика — один раз на класс.
- Внутри класса инициализаторы выполняются **в текстовом порядке**. `static final INSTANCE = new X()` выше `static int count = 0` — конструктор увеличит `count`, а следующая строка обнулит.
- Класс инициализируют: `new`, вызов статического метода, чтение или запись не константного статического поля, `Class.forName(name)`, инициализация подкласса.
- Не инициализируют: литерал `X.class`, обращение к константной переменной, создание массива `new X[10]`, обращение к статическому полю предка через имя наследника (инициализируется только предок).
- Ленивый синглтон holder-класса держится на этом: вложенный `Holder` инициализируется при первом обращении к `Holder.INSTANCE`, потокобезопасно силами JVM.
- Константная переменная: `final` + примитив или `String` + константное выражение. `static final Integer`, `static final List`, значение из вызова метода — не константы.
- Значение константы попадает в байткод потребителя. Новый jar с другим значением без пересборки потребителя ничего не меняет — и ошибок не будет. Меняющееся значение — не константой. То же для меток `case`.

## Вложенные классы
- С JDK 18 javac не добавляет `this$0`, если внешний экземпляр не используется и класс не `Serializable`. Надёжнее сразу делать вложенный класс `static`.
- «Двойные скобки» `new HashMap<>() {{ put(...); }}` — анонимный подкласс на каждое место, и `HashMap` сериализуем, значит в нестатическом контексте ссылка на внешний объект есть всегда. Замена — `Map.of(...)`.

## Объекты и неизменяемость
- Неизменяемый класс: `final` класс, `private final` поля, без сеттеров, и **копии** изменяемых входов и выходов: `this.members = List.copyOf(members)`.
- `record` неизменяем поверхностно: компоненты `final`, но список внутри можно менять. Копию делают в компактном конструкторе.
- `clone()` массива и `Object.clone` по умолчанию — поверхностные: вложенные объекты общие.
- Копирующий конструктор или фабрика лучше `clone`: у `Cloneable` нет метода `clone`, а `Object.clone` создаёт объект в обход конструктора.
- Встроенная сериализация: десериализация недоверенных байтов — путь к RCE (защита — фильтры JEP 290, JEP 415); объект восстанавливается в обход конструкторов (кроме `record`); без явного `serialVersionUID` новое поле или не-`private` метод ломает старые данные. Вместо неё — JSON, Protobuf, Avro.
